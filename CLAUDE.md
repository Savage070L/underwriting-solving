# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this app does

Browser-based underwriting toolkit for Standard Life (Казахстан, ОСНС — обязательное страхование работника от несчастных случаев). All processing is client-side — the user uploads Excel files locally, the app parses them in the browser and generates `.docx` documents and an analytics dashboard.

Live: <https://savage070l.github.io/underwriting-solving/>

## Running locally

There is **no build step** — the app is pure HTML/CSS/JS. To develop:

```bash
# any static server works; the project's `.claude/launch.json` uses:
npx http-server . -p 8085 -c-1
# then open http://localhost:8085/
```

For testing reference files locally without re-uploading every time, drop them into `test-data/` and read via `fetch('/test-data/<filename>')` from the browser console. The directory is `.gitignore`d (test files contain real БИНы and ФИО — personal data, never commit).

Deployment to GitHub Pages is automatic on push to `main` via `.github/workflows/pages.yml`.

## Architecture

### Two pages, one shared state

- `index.html` — form-driven document generator
- `analytics.html` — read-only dashboard

The dashboard does NOT re-parse files. When the user clicks "Открыть аналитический дашборд" on the main page, `App.openAnalytics()` serializes a *snapshot* into `localStorage['analytics_snapshot']` and opens the dashboard in a new tab. `analytics.js` reads that snapshot — if missing, shows the empty state.

If you add new derived data to documents, you must also add it to the snapshot in **both** places: `openAnalytics()` and `toggleInlineAnalytics()` in `js/app.js`. They're near-duplicates of each other.

### Tabs on index.html (one page, shared App state)

`index.html` is split into **tab-panel sections** (`.tab-panel#tab-{refs,contracts,contractor,decision}`). The nav (`.tab-nav`) lives **inside the header** (`.app-header-inner`, between the brand and `.app-meta`) — tabs use **SVG icons** (`.tab-btn-ico`), not numbers. It is **not** a multi-page app — all tabs share the in-memory `App` state and switching just shows/hides panels (no reload, nothing serialized). `App.switchTab(name[, scroll])` toggles `.is-active` on the panel + button and persists `localStorage['active_tab']`; `App._initTabs()` (called from `init()`) restores it, defaulting to `refs` when not all 6 refs are loaded, else `decision`. **Display order** (left→right, `App.TABS`) — the panel DOM order differs and doesn't matter:

1. **Проверка контрагента** — `#tab-contractor`: standalone БИН check: `#contractorBin` + «Проверить БИН» → `App.quickLookupByBin()` (which reads `#contractorBin`, not `#manualBin`). Renders the company profile only, no tariff.
2. **Проверка Договоров** — `#tab-contracts` / `#batch-section` (batch AR generation; see below).
3. **Андеррайтинговое решение** — `#tab-decision`: per-case files + manual full input (`#manualBin` + «Применить» → `applyManualZayavka`) + Шаги 1–3 + document generation.
4. **Справочники** — `#tab-refs` / `#refs-section` (the 6 reference files).

**Source links bar (`.src-links`).** At the very top of **«Проверка Договоров»**, **«Проверка контрагента»** and **«Андеррайтинговое решение»** (first child of each tab panel, above every block) sit two full-width external link cards: **egov.kz** → `https://egov.kz/services/P30.11/#/declaration///` («Резидентство: Выдача справки о регистрации (перерегистрации) юридических лиц… • справка P30.11») and **stat.gov.kz** → `https://stat.gov.kz/ru/cabinet/juridical/by/bin/` («Поиск юридического лица или индивидуального предпринимателя»). They open the portals manually — that's where the user signs in, and both our automated checks depend on those sessions (stat.gov ЭЦП session, egov Bearer pair). Plain `<a target="_blank" rel="noopener noreferrer">`. **Single source of truth: `<template id="tpl-src-links">`** near the top of `.container`; `App._renderSourceLinks()` (first call in `App.init`) clones it into every `.js-src-links` mount — do NOT paste the markup into a tab, add a mount div instead. Cards are `flex: 1 1 320px` so two of them split the row full-width and wrap on narrow screens; the service name wraps freely (`overflow-wrap: anywhere`) rather than being truncated.

**The cards double as connection indicators** (green `.is-ok` / red `.is-bad` / neutral `.is-checking`), painted by `App._paintSourceLinks()` from two mirrored state machines: `App.STATGOV` (revived — it was dormant after the header pill was removed; `check()` → `StatGovClient.health()`, states online/nologin/unreachable/offline) and `App.EGOV` (`check()` → `StatGovClient.egovHealth()` → bridge `EGOV_HEALTH` → `getEgovToken({passive:true})`, states online/nologin/offline). Both `init()` from `App.init`: on `sl:bridge-ready`, every 5 min, and on window focus. A red card is self-healing UX — the card IS the link to the portal where the user signs in.

**Re-check engine (`App._wireSourceChecks` / `_runSourceCheck` / `_scheduleSettle`)** — shared by both machines, which supply only their own `_probe()`. It exists because a single check-on-load assigns the WRONG status: the content script announces `BRIDGE_READY` at `document_start` (nobody listening yet) and at `DOMContentLoaded`, while the MV3 service worker may still be asleep — so the first probe times out and paints «нет расширения» on a working bridge. Guarantees:
- **A re-check requested while one is in flight is queued (`_again`), not dropped.** This was the actual sticky-status bug: the `sl:bridge-ready` re-check hit the `_busy` guard and returned, so the wrong state survived until focus or the 5-min timer.
- **Settle ladder after every page load** (`_RECHECK_LADDER_MS` = 800/2000/5000/12000 ms): while the probe still answers `offline` (bridge silent), retry; the ladder stops as soon as the answer is definite, so a working bridge costs exactly one probe.
- **Triggers**: init, `sl:bridge-ready`, 5-min timer, `focus`, `visibilitychange` (focus misses tab switches inside a window), and `pageshow` with `persisted` (bfcache restore re-runs no `DOMContentLoaded`, but sessions may have died meanwhile → full ladder again).
- **«Bridge missing» vs «source slow»**: if `health()` times out, a cheap local `ping()` decides — bridge answers → `unreachable` («недоступен»), silent → `offline`. Paired with an `AbortController` (7 s) inside the extension's `statgovHealth()`, whose un-timeouted `fetch` could hang longer than the app waited and thus masqueraded as a missing extension.

**Two verdict bugs found on live data (both fixed) — read before touching the probes:**
- **stat.gov false GREEN.** `session` was `hasSessid` — but `sessid` is a **Bitrix CSRF token present on the anonymous page too** (verified against the live HTML), so the card was ALWAYS green. The real markers: anonymous → `stat-authform` block + `authBySSO` + «Пожалуйста, авторизуйтесь» and **no `<input name="bin">`**; logged in → the БИН search field exists. `statgovIsLoggedIn(html)` = `searchField && !authForm`, and `fetchByBin` now checks it FIRST (it used to trust sessid and silently POST into the login page).
- **egov false RED.** The portal's Bearer pair lives in egov.kz `localStorage`, readable only through an **open egov.kz tab** or our cache — and `chrome.storage.session` is wiped by an extension reload / browser restart. With neither, we simply **do not know**, and «нужен вход» was a lie. Now: the pair is also persisted to `chrome.storage.local` (survives reloads; `egovPairUsable()` discards it once BOTH access and refresh are expired, so a stale pair can't fake green), `EGOV_HEALTH` reports `tabOpen`, and a new **`unknown` state** (neutral, «откройте egov.kz») covers "no pair + no tab" — red is reserved for what we actually KNOW: an egov tab is open and holds no usable session (`tabOpen`), a pair existed and expired on BOTH tokens (`hadPair`), or a recent hard failure (`paused`). **Every one of those flags must be forwarded by `StatGovClient.egovHealth`** — dropping `tabOpen` there (a real bug, caught on the user's live browser) made `!h.tabOpen` always true and left the red verdict unreachable. Neutral is also what `checking` paints: `_paintSourceLinks` colors green only on `online`, red only on `nologin/offline/unreachable`, everything else stays neutral.
- Also fixed while here: `getEgovToken`'s single-flight merged **passive and active** callers, so a real residency request could piggyback on the indicator's passive probe and skip its token refresh. Passive now waits for an active flight, never the reverse (`egovTokenInFlightPassive`).

Three more rules keep it from lying (the header pill was deleted precisely because a passive probe read «недоступен» while lookups worked):
- **Neutral until the first answer** — never green/red on assumption.
- **Trust window** (`_lastLookupOk` + `_TRUST_MS` = 10 min): a REAL successful lookup outranks the passive probe, so a probe hiccup can't turn a working bridge red. `App.STATGOV.noteLookup` fires from `autoLookupStatGov`; `App.EGOV.noteLookup` from `ResidentCheck.fetchEgovRaw` (success and the «сессия истекла» failure, which also zeroes the trust window).
- **Stale access + live pair ≠ red for egov**: the access token expires every 10 min by design and refreshes itself on the next request — only «no pair at all» or the extension's `egovNoSessionUntil` pause is a real problem.

**`EGOV_HEALTH` adds ZERO egov network traffic** — `getEgovToken({passive:true})` only reads the session cache / open tabs' localStorage and never spends the one-time refresh token. Keep it that way: an indicator must not become a request source (see the request-budget rules above).

**Batch generation ships the dossier next to every АР** (`BatchAR.generateAll`, button «Печать Досье + Рекомендации АР»). For each printed contract the ZIP also gets `Досье/Досье {номер}.html` — a **self-contained** page (`Dossier.fileHtml`): CSS inlined via `Dossier.ensureCss()` (no external `<link>` — the file travels alone), content pre-rendered into `#ds-root`, and the masonry script re-run on `load`. The dossier is per CONTRACT, not per party: it already carries both «Страхователь» and «Контрагент» cards, so it is built from the insurer side (`_ctxFromRow(idx, 'insurer')`). **It never calls `_enrich`** — batch verification has already filled the stat.gov/kyc/e-Qazyna/residency caches for those БИН, and re-fetching for hundreds of rows at print time would be exactly the request storm the egov budget rules forbid. A dossier failure is caught per contract and logged — it must never break document printing. The ZIP is named `Досье и АР пакет {дата} (N).zip`.

**Facsimile signatures in «Рекомендация ДАиП»** (`ARForm.SIGNATURES` + `ARFormPdf.sigCell`). Two signers sign this form: the ДАиП director (sections 1 and 3) and the risk manager (section 2). PNGs live in `assets/signatures/` and are rebuilt from the raw scans in `~/Downloads` by **`tools/build_signatures.py`** — never hand-edit them, re-run the script.

Rules that must not be broken:
- **The facsimile is bound to the SURNAME, not to the position** (`_sigFor` matches a lowercase substring of the effective name). Put a different person in the Справочники and their row prints the plain underscore line — another person's signature can never be stamped. Verified: signer «Петров П.П.» → no image, 37 KB instead of 65 KB.
- **Nothing is positioned absolutely.** The cell is `columns: [ФИО][прочерк + image][Подпись]`; the image sits in the same stack as the underscore run, so it follows the line wherever layout puts it. Horizontally it is centred on the line (`(LINE_W - w) / 2`, with `LINE_W` computed from the underscore count — in Times New Roman `_` is exactly half an em), which is why it no longer drifts with name length. Verified against filials, 2-line names, 12-digit sums, and a 12-филиал contract that spills onto page 2 — the signature stays on its line in every case.
- **Row heights must not change.** The image uses negative top/bottom margins so it overlaps the line without adding height; the form is tuned to one A4 page. Confirmed by comparing table-border coordinates with the unsigned version — pixel-identical.
- **Seat is per-signature on BOTH axes** (`dx` right / `dy` up, in mm, on each `SIGNATURES` entry: Джелкобаев `dx:2, dy:4.9`, Осинцев `dx:4, dy:2.6`). The images are trimmed to their ink, but the ink sits differently inside each box and **both signatures are WIDER than the underscore run (21 mm)** — Джелкобаев 25 mm, Осинцев 29 mm — so plain centring makes each overhang left by half the difference and collide with the ФИО, the wider one worse. `dx` compensates exactly that; `dy` fixes the vertical seat. Values were matched pixel-for-pixel against files the user positioned by hand. Sign of `dy` is inverted: **lower `dy` = lower signature**.
- **The PNGs are print assets, not web icons** (`tools/build_signatures.py`). The raw scans are photos of a blue gel pen with the background knocked out, which leaves three defects that all print as grey mush: the stroke is semi-transparent and light, it has pale streaks *inside* it (background removal ate part of the line), and grey-white dust floats around it. The script works at the scan's full resolution — coverage from the composite-on-white luminance (folds alpha and lightness into one number), despeckle by neighbour support, morphological closing to refill the streaks, gamma + dilation to strengthen the stroke, a light blur to smooth the ragged edge — and only then downsamples. Output is **one single ink colour (`INK`) with a graded alpha**, so a grey or white pixel cannot exist in the file by construction. **480 px tall ≈ 690 dpi** at the 17.7 mm print height; the old assets were 300 px *wide* (~270 dpi) and quantised to 64 colours, which banded the alpha — that combination was the visible pixelation on paper.
- **Format must be RGBA, never a palette PNG.** pdfmake splits an image into a colour layer + an `/SMask`; with a constant ink colour the colour layer deflates to ~1 KB and only the alpha costs anything. A palette PNG is smaller on disk but lands in the PDF **twice** (indices *and* SMask) and doubles the document — measured 388 KB vs 213 KB.
- **Declare facsimiles in `docDefinition.images` and reference them by key**, never inline the data URL in the node. The ДАиП director signs sections 1 and 3, and pdfmake embeds a repeated inline data URL as two separate XObjects (+60 KB on every document of a batch). With the dictionary a signed document is ~119 KB (unsigned 37 KB).
- **Signature rows are enlarged** so the facsimile is legible in print (`SIG_HEIGHT` 67 px ≈ 17.7 mm; the row is `max(SIG_ROW_K × natural, signature + SIG_ROW_PAD)`, set through pdfmake's `table.heights` as a MINIMUM). Two traps here: the row must be driven by the **signature height**, not only by a multiplier — otherwise the image does not fit and spills onto neighbouring rows; and the vertical anchor is a **fraction** of the signature above the line (`SIG_ABOVE`), not its bottom edge, so the seat stays put when the size changes. Enlarging costs page space: contracts with 3+ филиалов now need a second sheet.

pdfmake cannot vertically centre table cells, so `_docDefinition` does it: it counts how many lines each cell takes using **real Times New Roman advance widths** (`PDF_CHAR_W`) and adds half the difference as a top margin. Without this, a one-line value sits at the top of a row whose label wraps to two or three lines («Руководитель Службы управления рисками» → «Осинцев Р.С.»).

**«Печать рекомендаций ДАиП» is NOT a tab** — it was one (`#tab-daip`) and is now the `#daip-block` at the **very bottom of «Проверка Договоров»** (`js/daip-print.js`, `DaipPrint`), because it works off the same registry. It prints the **same full 3-section form as the batch button above it** (Рекомендация ДАиП → Заключение подразделения по управлению рисками → Андеррайтинговое решение; one doc per contract, филиалы inside) to a ZIP. **The document structure is identical — do NOT strip sections here**; it differs from «Печать Досье + Рекомендации АР» in exactly two ways: it prints **all** contracts including the red/error ones (batch generation excludes them), and the signer is editable. `DaipPrint.refresh()` (count + button state) is called from `BatchAR._updateControls()` — i.e. on every load/clear/aggregate tick — and from `App.switchTab('contracts')`. **No stat.gov.kz gate.** Editable signer via `#daip-signer-role` / `#daip-signer-name` → `ARFormPdf.buildPdf(row, {underwriterRole, underwriterName, filials})`; files are named `Рекомендация ДАиП {номер договора}.pdf` (batch names them `АР {номер}.pdf`). The signer field is **prefilled from the Справочники** (it used to be hardcoded «Бурханов Д.К.» in the markup, which silently overrode the reference table). Reuses `BatchAR._ensureZip` / `saveAs`.

**stat.gov.kz status indicator — REMOVED.** The header pill (`#statgov-pill` / `.app-meta`) that showed the bridge connection status was removed at the user's request (the passive probe could read «недоступен» while lookups actually worked). The `App.STATGOV` object still exists and its `noteLookup`/`_set` are still called from `autoLookupStatGov`, but they no-op now (no `#statgov-pill` element) and `App.STATGOV.init()` is no longer called from `App.init()` (no polling). The `STATGOV_HEALTH` bridge message + `statgovHealth()` remain in the extension but are unused by the app. To re-add a status UI, restore the `.app-meta` pill in index.html and the `App.STATGOV.init()` call.

**Per-tab profile render: the DOSSIER is the profile now.** `showPreview()` (single update path, reads `App.zayavka`) no longer builds field cards — both tabs show the same embedded dossier (`Dossier.renderSingle()`, one context, two mounts):
- **Андеррайтинговое решение**: broadcast to all `.js-preview-grid` / `.js-preview-panel` — no-discount `badges` + `<div class="ds-mount" id="dossier-decision">` + the stat.gov status plate (`sgStatus`: loading / error with the «установи расширение» hint / not-found). The old «Основная информация» card, ОКЭДы subsection and collapsible «Подробности» (`mainRows`/`detailRows`/`renderItems`/`okedsSubBlock`/`togglePreviewDetails`) were **removed at the user's request** — every one of those fields lives in the dossier (banner KPI strip, party card, «Деятельность и тариф», Резидентство/Гос. участие cards, «Справочные коды»).
- **Проверка контрагента**: `#preview-grid-contractor` (deliberately **no** `.js-preview-grid` class, so the broadcast skips it) gets the ИИ-советник по ОКЭД (`App._okedAdvisorHtml()`) + `<div class="ds-mount" id="dossier-contractor">`. The old «Информация о контрагенте» card + ОКЭД list were likewise removed. **No discount alerts here at all** (neither the `badges` banner nor the `.js-young-alert` div — `#young-company-alert-contractor` was deleted from index.html at the user's request): this tab computes no premium/discount, so «Скидка не применяется: компания младше 3 лет» is noise here; the warning lives only in «Андеррайтинговое решение», and the company's age is visible in the dossier KPI strip.

Both keep `.js-preview-panel` (visibility toggle). They share `App.zayavka`, so a БИН check in **Проверка контрагента** and a loaded case in **Андеррайтинговое решение** overwrite each other (acceptable — one workflow at a time). The young-company alert (`.js-young-alert`) and avg-salary alert (`.js-avg-alert`) live only in the **Андеррайтинговое решение** tab. When adding a new profile-render target, add its mount id to `Dossier._SINGLE_MOUNTS` instead of building a new card.

### Reference files and caching

The app expects **6 reference files** uploaded once and cached in `localStorage`:

| File | `App.refData` key | Purpose |
|---|---|---|
| Поправочные коэффициенты | `popravka` | Tariff per risk class + adjustment matrix |
| Норматив | `normativ` | Company assets, portfolio share, by month |
| КУ по классам | `ku` | Portfolio loss ratio (updates monthly) |
| Калькулятор рентабельности | `calculator` | Death/injury rates per ОКЭД |
| Классификатор ОКЭД | `classifier` | ОКЭД → risk class + activity name |
| Аффилированные лица | `affiliated` | List of related parties (БИН/ИИН + name) |

Plus **2 per-case files** (not cached): заявка `.xlsm` and история убытков `.xls`.

`App.refData` is restored from `localStorage` on init (`App.restoreCache`). The case (zayavka + claims + binData) is also persisted (`App._persistCase` / `_restoreCase`) so navigating back from the analytics dashboard does not lose loaded files.

### Document generators

Four generators in `js/`, all consume the same `data` object produced by `App._collectData()`:

- `ar-generator.js` — Андеррайтинговое Решение (АР)
- `zakl-generator.js` — Заключение департамента
- `protocol-generator.js` — Протокол заседания АС / Правления
- `sz-generator.js` — Служебная записка (`mode: 'pravlenie' | 'sd' | 'as'`)

To add a field to documents, edit `_collectData()` in `js/app.js` (single source of truth for document inputs), then reference `data.<field>` in the generator(s).

All four generators must reflect the **risk decision** (`data.verdict`, from the «Решение по риску» block) through **one shared source of truth: `Utils.acceptedConditions(data)`**. It returns `{verdict, decision, useAdjusted, coeffEffective, finalPremium, conditionText}` — the underwriter's manual verdict **always wins over the algorithm** (ФИНАЛЬНОЕ решение за андеррайтером): `accept_standard` → standard conditions, `coeffEffective=1`, `finalPremium=premiumBase`, **no discount shown even if `data.coeffDown>0`**; `accept_adjusted` → the ПК/discounted premium, but only when `coeffDown!=0`; `reject`/`defer` → no premium recommendation. **Do not read `data.coeffDown` / `data.verdict` directly in a generator** — always go through `acceptedConditions` (this is exactly the bug that made `zakl-generator.js` show an algorithmic discount under a manual «стандарт» verdict). The condition clause (standard / lowered / raised / «повышенным или пониженным») comes from `conditionText` (built on `Utils.acceptanceConditionText`). The **final limit documents** — `protocol-generator.js` («Принято РЕШЕНИЕ») and `sz-generator.js` — derive their final wording from `verdict` (reject → «отказать… в связи со степенью риска»; defer → «отложить… на определенный срок»); СЗ/АР/Заключение show the ПК-adjusted premium **only** when `useAdjusted` is true. **The «с ПК» line must be ABSENT, not printed with a repeated base value or a dash, when no discount applies** — both СЗ builders used to emit it unconditionally (`generateAs` repeated `premiumBase` under the «с ПК» label; the Правление/СД builder printed «с учетом ПК: -»), so a memo for a company with 45 НС read as though a discount had been granted. The rule is not specific to claims: `useAdjusted` already covers every reason the discount is dropped (НС, компания моложе 3 лет, премия ниже 1 МЗП, ручной «стандарт»), so with no ПК the memo carries exactly one field — «Страховая премия». The AR form is the one exception: its п.16 is a fixed numbered row of the blank, so it keeps printing «-».

**Discount (понижающий ПК) floor — `App._effectiveCoeffInfo()` in `js/app.js` is the single computation point.** The discount (`coeffDown`) is removed entirely (set to 0, not clamped) when: there were НС in the last 3 years (`noDiscountReason='claims'`), the company is younger than `minCompanyAgeYears` (`'young_company'`), **or applying it would drop премия-после-ПК below `minPremium` (1 МЗП = 85 000 ₸) (`'below_min_premium'`)**. The повышающий coefficient (`coeffUp`) is always kept. Exactly 85 000 after ПК is allowed (half-tiyin epsilon). `data.coeffDown` from `_collectData` is already this effective value, so the rule propagates to every document automatically. Affiliation does **not** affect the discount — it only routes the organ to СД.

When interpolating a count next to a Russian noun («3 работника», «5 траншей»), use `Utils.plural(n, one, few, many)` / `Utils.pluralize(...)` — never hard-code one form. Destructive UI actions (clearing reference/case files, section reset) must go through `App.confirmDialog({title, text, confirmLabel})` (markup `#confirm-overlay` in index.html).

### Resilient parsers (important)

Reference files like КУ по классам get **monthly updates** — rows shift, new classes get added, columns sometimes reorder. The parsers in `js/excel-reader.js` are designed to find data **by content** (label text), not by hard-coded coordinates. When extending or fixing parsers:

- Find header rows by searching for label text in early rows (e.g. «Итого», «Класс»+«Тариф», «Среднегодовое количество пострадавших»).
- Read data dynamically from that point until empty rows or until reaching another label.
- **Beware sparse arrays**: `XLSX.utils.sheet_to_json({header:1})` returns sparse arrays with holes. `findIndex`/`find` callbacks receive `undefined` for holes — always build dense lowercased arrays (`for (let j=0; j<row.length; j++) out[j] = String(row[j]||'').toLowerCase()`) before scanning headers.

`readZayavka` is still position-based (D8, G8, D11–D20, E21, G21) because it parses a strict company template. If the заявка template ever changes structure, this parser will need the same context-based treatment.

### ОКЭД override flow

`App._resolveOked()` is the single entry point used by `_collectData`, `showPreview`, `openAnalytics`, `toggleInlineAnalytics`. Priority:

1. Manual input in `#okedInput` (overrides everything)
2. Among the company's stat.gov.kz ОКЭД — the one whose class has the **highest tariff** (`App._tariffByClass`, NOT the highest class number; mapping is non-monotonic — see batch section). `source: 'statgov-max-tariff'`.
3. ОКЭД from заявки (D9)

Returns `{oked, riskClass, activity, source}`. Class and activity are resolved through the classifier using `Utils.lookupOked()`:

1. Exact match first (e.g. `'07298'` → cls 21, even if `'07xxx'` would match cls 11).
2. Then prefix match (`'72xxx'` matches input starting with `72`), but **skips** the row if the input is listed in column D exceptions.

## Batch AR generation (реестр → .docx)

A separate workflow from the single-case form: upload the daily contracts export (one `.xlsx`, ~115 rows) and generate a filled **Андеррайтинговое решение** as an editable **Word `.docx`** per ОСНС contract, named `АР {БИН}.docx`, bundled into a ZIP. Lives in its own tab on `index.html` — **«Проверка Договоров»** (`#batch-section`, tab `#tab-contracts`; the section header was renamed from «Массовая генерация Рекомендации ДАиП» but the code/module names still say *batch*). Three modules:

- `js/batch-reader.js` — `BatchReader.parse(arrayBuffer)`. Finds columns **by header text** (row 1) with column-letter fallback (export is stable but resilient anyway). Filters to ОСНС rows with a valid 12-digit БИН. **The export template was extended (49 → 52 columns) and positions shifted; header-text matching absorbs that, so both templates parse.** Three fields are new: **`ДатаДоговора`** → `row.dateContract` (see below), **`СтранаРезидентстваСтрахователя`** → `row.residencyCountry` (drives the single «Резидент» column — see the residency section), and **`Автор`** → `row.author`, which now **takes priority over `Менеджер`** (`headers: ['автор','менеджер']`) — the batch table column is «Автор». Key mapping (confirmed against a real export): БИН=H, Номер договора=D, Страхователь=BR, даты=B/K/L, Страховая сумма=V, ФОТ→ГФОТ=BY, Количество объектов→workers=AL, Класс проф риска=AK, Код ОКЭД=AJ, Вид деятельнсти Андеррайтеры=CA, **Поправочный Коэфициент=CM (1→standard, 0,9→discount)**, **Страховая премия без коэф=CU (premium before)**, **Страховая премия=W (premium with ПК = CU×ПК)**. `tariff = CU / V` (self-consistent with the risk class — no popravka reference needed).
- `js/ar-form.js` + `js/ar-form-pdf.js` — **the form is printed as PDF, not .docx** (facsimile signatures are embedded, and a signed document must not be editable; the old docx builder was removed — it is in git history). `ar-form.js` keeps the DATA and RULES (formatters `_money/_pct/_int/_dateRu`, `_effName`, `decisionText`, column geometry `COLS` in twips, signers and facsimile); `ARFormPdf.buildPdf(row, opts)` → `Blob` builds the markup. Same 3-section form from the `Андеррешение_ОСНС.XLS` sheet «АРешение» as **one 9-column table** (label + 8 financial columns), **one A4 portrait page** (1cm margins, 8pt body / 6.5pt headers). Built with **pdfmake** (`js/lib/pdfmake.min.js`) and **Times New Roman embedded** (`js/lib/pdf-fonts.js`, subset to Latin+Cyrillic+№+dashes: 806 KB → 23 KB per weight; note ₸ is NOT in Times New Roman — this form writes «тг.»). Default underwriter **Джелкобаев Т.К.** (ДАиП director since 01.07.2026) / role «Андеррайтер» (`ARForm.UNDERWRITER`), overridable via `opts.underwriterName` / `opts.underwriterRole`, but the real default comes from the **Справочники** signer table (`App._getSigner('daipDirector')`, risk manager from `asMember4`). **All three sections are always emitted** — both callers («Проверка Договоров» and «Печать рекомендации ДАиП») get the identical document; there is no single-section mode (a former `opts.only === 'recommendation'` flag was removed — the ДАиП tab must print the full form). document № = contract number (col D). Also exposes formatting helpers (`_esc`, `_money`, …) used by the preview table.
- `js/batch-ar.js` — `BatchAR` controller: parse → preview table → **PDF** per contract via `ARFormPdf.buildPdf`, batch → **JSZip** (lazy from CDN, `compression:'STORE'`). **Generation is gated on stat.gov.kz**: the "Печать Досье + Рекомендации АР" button stays **disabled until `_verifyComplete()`** (extension connected AND every row `statgovStatus==='done'`). No connection → rows `skip`, blocked, "Повторить проверку" (`retryStatgov()`). Verification runs **two decoupled pools in parallel** so neither waits on the other: statgov (`STATGOV_CONCURRENCY=6`, the gate — its lookup is a plain fetch in the extension, not tabs, so high concurrency is fine) and **e-Qazyna gov-participation** (`_poolEgov`, `EGOV_CONCURRENCY=8`, via `App.WORKER_URL`). A **kyc.kz fallback** (`KYC_CONCURRENCY=5`, via `StatGovClient.lookupKyc`) fills **registration date + legal address** only for rows where stat.gov returned no reg date, and now runs **in parallel with statgov** — each row is queued for kyc (`_maybeQueueKyc`) the moment its statgov lookup closes with no date, drained by `_pumpKyc` (dedup by БИН, in-flight cap), not one pool after the whole statgov pass. `_maybeFinishKyc` sets `_kycFinished` when statgov is fully done + kyc queue empty + none in flight. Effective values: `_effRegDate` (statgov → kyc) drives the «Дата рег.» column and the young-company age «2 года 4 месяца» shown under the date; `_effLegalAddress` (statgov incl. «Местонахождение» for ИП → kyc) feeds the document address. The «Дата рег.» column shows only the date (no visible `kyc` badge / no БИН-derived month-year note — removed as noise), and **⏳** until `_kycFinished`. UI updates are batched via `_scheduleAggregate` (rAF). Preview columns: `# · БИН · Страхователь · ОКЭД · Класс · Кол-во сотрудников · ФОТ · Страх. сумма · Страх. Премия · ПК · Премия с ПК · Дата рег. · Гос. участие` — ОКЭД/Класс are two-line (выгрузка top, statgov/computed bottom; класс lists per-OKED classes in OKED order). Discrepancies are highlighted at **two levels** (helpers `_okedError`, `_classDiff`, `_govDiff`, `_rowLevel` in `batch-ar.js`): **red** (`batch-row--err` / `batch-cell--err`) for a hard data error — the выгрузка ОКЭД is **absent from the company's stat.gov.kz ОКЭД list** (so the derived class is wrong too), or e-Qazyna gov-participation ≠ выгрузка; **yellow/amber** (`batch-row--warn` / `batch-cell--warn`) for a **soft** class mismatch — the ОКЭД is valid for the company but the выгрузка didn't pick the **highest-tariff** class. **CRITICAL: the "correct" class is the one with the maximum insurance TARIFF, NOT the maximum class number** — the class→tariff mapping (from `popravka.riskRates`) is non-monotonic (e.g. class 13 = 1.29% is higher than class 16 = 1.17%, so for {4,6,13,16} the right class is **13**, not 16). `BatchAR._maxTariffClass(classes)` (using `_tariffByClass`) replaces every `Math.max(...classes)` — used by `_computedClass` (страхователь), `_contrComputedClass`/`_contrClassDiffByBin` (контрагент); the same rule drives `App._resolveOked()` (active ОКЭД = max-tariff, via `App._tariffByClass`, not max class) so contractor-check and underwriting also use the max-tariff class. Falls back to max class number only when no tariffs are loaded. **Soft mismatches are flagged only when a high class is involved (≥ `_CLASS_WARN_MIN` = 13)** — discrepancies among classes 1–12 count as normal (green). Страхователь uses `_classDiffWarn` (threshold-gated; raw `_classDiff` still feeds the red «ОКЭД absent + class wrong» branch); контрагент threshold lives inside `_contrClassDiffByBin`. **A ПК ≠ 1 cancels the yellow row entirely** (`_pkAdjusted(r)` in `_rawRowLevel`): a discount or surcharge means the underwriter already reviewed that contract by hand, so the soft ОКЭД/class mismatch is a known, accepted story and must not come back as work — such rows drop out of the «расхождений» counter, the «Ошибки» filter and the yellow xlsx export. **Red errors are unaffected** — bad data stays bad whatever the ПК (incl. `_pkYoungError`, discount on a young company). The class **cells** keep their amber marker so the mismatch is still visible, with a tooltip (`_pkWarnNote`) explaining why the row is green. `_pkAdjusted` guards `coeff == null` and `coeff == 0` explicitly — `Number(null)` is `0`, which would otherwise read as «≠ 1» and silently clear the yellow for rows with no ПК at all. Alignment: БИН/Страхователь/Дата рег. left, everything else centered (header and value share the column-class `text-align`). e-Qazyna gov logic: **found in the registry → «Да», not found → «Нет»** — the **share is NOT shown** (computed only to infer found/not-found); gov participation by itself is **never** highlighted, only a выгрузка↔e-Qazyna mismatch (red).


**Filter chips, not sorts.** The chip row above the table (`#batch-sort-chips`, rendered by `_renderSortChips`) used to be «Сначала …» toggles that only pushed matching rows to the top. They are now **filters**: an active chip leaves ONLY matching rows in the table. Definitions live in **`BatchAR._FILTER_DEFS`** (`{key, icon, label, title, match(row)}`) — «⚑ Ошибки» (`_rowLevel(r)` is err **or** warn), «🏢 Филиалы» (`_isFilial`), «⏳ Транши» (`_trancheCount > 0`), «🌐 Нерезиденты» (`_residRowRank >= 2` — нерезиденты **and** ИП, whose residency isn't computable), «🟪 АС лимиты» (`_overAsLimit`). Active keys are in `BatchAR._filters` (was `_sorts`), toggled by `toggleFilter(key)`. **Several active chips combine with AND** (each is a separate attribute, so each chip narrows the view) — `_displayOrder()` keeps rows where `every(match)`, in file order, and then applies two orderings: **«Ошибки» puts the red rows first, then the yellow ones** (the underwriter works down by descending severity; file order is kept inside each rank), and «Филиалы» groups by contract number so branches sit together. With **both** on, the rank is taken per **contract** (`_groupLevel`), not per row — otherwise the rows of one contract would split between the red and the yellow block. Ranks are precomputed into a `Map` before `sort` (calling `_rowLevel` from the comparator would re-run every row check O(n log n) times). When the combination matches nothing, `_renderScrollInfo` says so explicitly («Под фильтр X + Y не подошла ни одна строка из N») — an empty table would otherwise read as a bug. When adding a chip, add one `_FILTER_DEFS` entry (button, active state and the HTML-report header line come for free) plus a `.batch-sort-btn--<key>` colour rule.

**«АС лимиты» + the purple row outline.** `_overAsLimit(row)` answers «is this row's contract over the АС limits?» by running the existing per-contract `_exceedsAsLimit(group)` (class 1–15 over `limitAsLowCls1_15`, class 16–22 over `limitAsLowCls16_22` — both editable in «Справочники», read through the single helper `_asLimits()`) over `_groupByContract()` once and caching the contract numbers in `_asLimitContracts` (reset with the other caches on load — recomputing groups per row would be O(n²) on a 16 k registry). **The comparison is `>=`, not `>`** — same as the «Справочники» hint («сумма ≥ этого → АС») and `Utils.determineOrgan` for the single case, so a contract at exactly 2 000 000 000 ₸ goes to АС (round sums are common in real registries; it used to be excluded here but included in the single-case flow). Every such row gets the class `batch-row--aslimit` → a **purple outline** drawn with `inset box-shadow` on its cells (top/bottom on all cells, left/right on the first/last), never a background: the row fill already encodes the check status, and a real `border` would shift the columns. Err/warn cells keep their own outline inside such a row. Editing either threshold in «Справочники» calls `BatchAR.invalidateAsLimits()` from `App.onLimitOverride` — it drops the cache and re-renders, **debounced 350 ms** because the inputs fire on `oninput` (one keystroke = one re-render otherwise). The check does **not** depend on stat.gov.kz (class and СС come from the выгрузка), so the outline, the chip filter and the status-bar counter are correct from the moment the file loads.

**No pagination — one scrolling table, rows appended in chunks.** The table used to be paged (`_page`/`_pageSize`, `_renderPagination`, `gotoPage`, `setPageSize`) — all removed. `renderTable()` now computes `_order = _displayOrder()` over every row but puts only the first `CHUNK` (200) into the DOM; `_appendChunk()` adds the next 200 whenever the user scrolls within `SCROLL_MARGIN` (900 px) of the bottom (rAF-throttled listener installed once by `_hookScroll`), and `#batch-scroll-info` shows «Показано N из M» + a «Показать ещё» button until everything is in. **Never render all rows at once**: measured on a real 16 477-row registry that is ~62 MB of HTML and hangs the tab for 30 s+; chunked, the first paint is ~340 ms and each chunk ~29 ms. Two supporting pieces: `_rowHtml(i)`/`_rowsHtml(idxs)` build row markup from data (so the HTML report can materialise **all** rows into a detached `<div>` without touching the live table — `downloadResults` no longer re-renders the page, ~1.8 s for 16 k rows), and `_rowEls` (idx → `<tr>`, filled by `_indexRows`/`_appendChunk`) replaces the `querySelector` in `_refreshRow` (0.7 ms → ~0 per call, and rows not yet in the DOM are skipped — they render up to date when their chunk arrives). Sorting re-renders from the first chunk and scrolls the table back to the top.

**Status bar** (`#batch-statusbar`) starts with the **progress** stat — `<b id="bs-done">/<b id="bs-total"> проверено` + a 108 px bar (`#bs-progress-bar`) + percent (`#bs-progress-pct`), where **`done = ok + warn + err + approved`** — only rows with a real verdict. **«Не проверено» (`statgovStatus` `skip`/`error`) must NOT count as done**: without the Chrome bridge every row is `skip`, and counting them showed «29 017 / 29 017 · 100 %» next to «0 корректных» (the bug this formula replaced). Percent is floored and clamped to 99 % until `done === total`, so 999/1000 never reads 100 %. Colour: indigo while checking, **green `.is-complete`** only when everything has a verdict, **amber `.is-stalled`** when the pass has finished but rows stayed unchecked (nothing in `checking`/`pending` and `done < total`); the tooltip then names the unchecked count — then the per-state chips (ok/warn/err/checking/pending/unchecked/approved; the last four hide at zero). After a `.batch-stat-sep` comes the **purple «N АС лимиты» chip** (`#bs-aslimit`): it is **not** a check state but a second axis — a row over the limits is *also* green/yellow/red — so it is not part of the ok+warn+err sum and is deliberately outside that group. It counts **rows** (like the neighbouring chips) via `_overAsLimit`; the tooltip carries the contract count and the current thresholds from «Справочники». Then the bar ends with the «↗ Открыть в отдельной вкладке» button (`margin-left:auto`; it used to sit in its own `.batch-toolbar` above the table, now removed). All of it is written by `_updateControls()`, which also calls `DaipPrint.refresh()`.

**Company age for the ПК is measured at CONTRACT DATE + 5 days, not today** — `BatchAR._ageRefDate(row)` = `row.dateContract` + `BatchAR.AGE_REF_GRACE_DAYS` (5 — the window in which the underwriter reviews the contract). **The contract date is `row.dateContract`, and its source is the `ДатаДоговора` column** («03.08.2026 0:00:00» — the time is stripped); only when that column is absent (old template) does it fall back to deriving digits `[2..8)` = ДД.ММ.ГГ from the contract **number** (`BatchReader._contractDate()`). The two genuinely differ — e.g. number `042407261200001` implies 24.07.2026 while `ДатаДоговора` is 03.08.2026 — and the column wins. **This date is the document date for every package** (АР, Заключение, Протокол, СЗ, batch АР/ДАиП), including the spelled-out «от «03» августа 2026 г.» forms: `applyRegistryRow` sets `docDate = row.dateContract || periodFrom || today` (it used to prefer `periodFrom`), and `ARForm` prints `row.dateContract`. Eligibility for the discount is fixed when the contract is signed, and the export is usually reviewed weeks later, so «today» let a company cross the 3-year line *after* signing and made an unlawful ПК look fine. `_applyYoung` computes `ageYears`/`youngAlert` against that reference. The **displayed** age under «Дата рег.» uses `_ageShownRef(row)` — the contract date **without** the 5-day grace (`_ageText(regRaw, refDate)` takes the reference explicitly) — because the underwriter wants to read the age as of the contract date; the `title` (`_ageShownTitle`) spells out both («Возраст на дату договора DD.MM.YYYY (право на ПК проверяется на +5 дней)»). Keep the two apart: `_ageRefDate` decides the flag, `_ageShownRef` only labels it. The `binDate <= now` guard in `_applyYoung` deliberately still compares with *today* — it only rejects a nonsense future founding date. (The single-case tab already did this: `App._effectiveCoeffInfo` uses `z.periodFrom || z.docDate`.)

File names: contract numbers contain slashes (`T04/290526/0002`), so **`BatchAR._safeName()` maps `/` and `\` to a hyphen** (not `_`: closer to the original, and inside a ZIP a `/` would silently create a folder), other Windows-forbidden chars (`:*?"<>|`) to `_`. Both `BatchAR._fileName` («АР {номер}.docx») and `DaipPrint._fileName` («Рекомендация ДАиП {номер}.docx») go through it — don't re-implement the sanitizer.

**PDF, not .docx** — the document carries facsimile signatures, so it must not be editable (~119 KB/doc with signatures, ~37 KB without). Duplicate contract numbers get `(2)`, `(3)` suffixes. To verify layout/one-page in Node: build `ARFormPdf._docDefinition(row, {signatures})` and feed it to `pdfmake/src/printer` (PdfPrinter) with the subsetted TTFs, then count `/Type /Page` in the output.

## BIN lookup architecture (CORS-critical)

The address (`pk.uchet.kz`) and gov-participation (`gr5.e-qazyna.kz`) APIs are blocked by CORS from any browser. A Cloudflare Worker (`worker/index.js`) proxies these requests with `Access-Control-Allow-Origin: *`. The Worker URL is hardcoded in `js/app.js` as `App.WORKER_URL`.

If the Worker goes down or the URL changes:
- Update `App.WORKER_URL` in `js/app.js`
- Redeploy the worker: `cd worker && wrangler deploy`
- The app degrades gracefully — БИН-поиск просто не отдаёт данные, all other features still work.

Do **not** try to call those APIs directly from the page — CORS will block it.

Beyond the Worker, the Chrome extension (`chrome-extension/`, "мост к stat.gov.kz") proxies browser-side sources via `StatGovClient` (page↔extension `postMessage` bridge): `STATGOV_LOOKUP` (stat.gov.kz, needs ЭЦП session — name/OKED/КРП/address/reg date), `STATGOV_HEALTH` (lightweight connectivity probe — Step-1 GET only, no БИН, reports `{reachable, session}`; drives the header `#statgov-pill`), `STATSNET_LOOKUP` (statsnet.co — industry, slow, opens tabs), `KYC_LOOKUP` (**kyc.kz, no auth** — base card parsed from the SSR `window.__NUXT__` IIFE without eval; see `chrome-extension/README.md`), and **`EGOV_RESIDENCY_LOOKUP`** (**egov.kz, needs the user logged into egov** — after the portal redesign it is `GET https://fgw.egov.kz/v1/P3011/organizations?bin={bin}` with a **Bearer token**, see «egov after the redesign» below; the **authoritative residency source**). kyc is the registration-date/address fallback in batch generation. `Utils.statgovLegalAddress(sg)` resolves the legal address from a statgov object, falling back to «Местонахождение …» in `sg._raw` (ИП have no «Юридический адрес»). After changing extension `host_permissions`, the user must reload the unpacked extension.

## Residency check (ГБД ЮЛ, offline index)

«Признак резидентства» is derived automatically from the БИН: **present in ГБД ЮЛ → резидент, absent → нерезидент**. Source dataset — [gbd_ul](https://data.egov.kz/datasets/view?index=gbd_ul) (реестр юр. лиц, филиалов и представительств РК, 986 136 records / 757 231 unique БИН).

**No per-БИН network call.** Unlike gov-participation (e-Qazyna) or stat.gov.kz, which are polled row by row, the whole БИН registry ships with the app as a compact binary index and is loaded once per page:

- `tools/build_gbd_index.py` → `data/gbd_ul_bins.bin` (~0.8 MB) + `data/gbd_ul_meta.json`. Format `GBDB v2`: magic + version + `uint32 count` + `uint32 flaggedCount` + LEB128 stream of **deltas** between sorted БИН (БИН < 10¹² is exact in a double), then the same stream for flagged БИН + one status byte each. Run `python3 tools/build_gbd_index.py --refresh` (measured: 16 min / 936 309 records / 15 retries) or rebuild from a CSV dump (`--csv`).
- `js/resident-check.js` → `ResidentCheck`. Auto-loads on script include, decodes into a sorted `Float64Array` (~16 ms), lookups are binary search. `ResidentCheck.check(id)` returns `{status, nonResident, registryStatus, label, badge, title}`.
- **The index rebuilds automatically once a week** — [`.github/workflows/refresh-gbd-index.yml`](.github/workflows/refresh-gbd-index.yml), Sunday 15:30 UTC (~20:30 Almaty). One self-contained job: run the build script → commit the new `data/*` → deploy Pages → email the result (`if: always()`, subject switches on `job.status`). It does **not** depend on `pages.yml` firing (a `GITHUB_TOKEN` push wouldn't trigger it), so it deploys inline via `configure-pages`/`upload-pages-artifact`/`deploy-pages`, sharing the `concurrency: pages` group. Email needs two repo secrets — `MAIL_USERNAME` (Gmail) + `MAIL_PASSWORD` (Gmail **App Password**); without them only the email step fails. **Safety invariant:** `build_gbd_index.py` returns non-zero and writes nothing when the scan is incomplete (`stats['complete'] == False`), so a flaky egov run can never overwrite the good index with a partial (БИН-dropping) one. Companies registered after the last successful build read as нерезидент until the next run; build date is in the UI («ГБД ЮЛ от DD.MM.YYYY») and `meta.generated`. Manual rebuild: `python3 tools/build_gbd_index.py --refresh`.
- **Deployable as static files.** The index (`data/gbd_ul_bins.bin` + `data/gbd_ul_meta.json`) is committed (NOT gitignored) and served by GitHub Pages like any asset; `resident-check.js` fetches it by **relative** path (`data/gbd_ul_bins.bin`), which resolves under the `/underwriting-solving/` Pages subpath. No CORS, no Worker — it's same-origin. Safe to publish: the file holds **only БИН numbers** (public legal-entity IDs), no names/addresses. Pages serves it with `Cache-Control: max-age=600`, so a redeploy propagates within ~10 min.

**The egov API stalls on long scans** — the TCP connection stays established and no response ever arrives (observed at ~61% of a full walk). Hence a short 45 s timeout with 8 retries, and, more importantly, **resume**: every page is appended to `data/.gbd_ul_scan.tmp` (`bin;day;modern;status`), so re-running the same command continues from the last cursor instead of starting over. `--restart` forces a clean run; the draft file is deleted once the scan completes and the count check passes.

**Never walk the dataset with plain `from`/`size`.** Elasticsearch behind data.egov.kz does not keep a stable order across deep offsets (`from` ≈ 900 000), and a naive scan **silently drops records**: measured on a real run, 655 of 753 520 БИН went missing — live registered companies that would have been labelled нерезидент. The downloader therefore pages with a **cursor**: `query = range(bin > lastBin)`, `sort = bin asc`, `from = 0` on every request, discarding the trailing same-БИН group so duplicates are not cut in half. `search_after` is rejected by the API (400), hence the range-based cursor. After the scan the script compares the number of records read with `totalCount` and warns if they diverge (a live registry may shift by a few records mid-scan; the tolerance is 0.1%). Records with an empty `bin` (~50 K, they duplicate BIN-bearing rows) are skipped by starting the cursor at `''`.

**Duplicates = re-registration; the index keeps the newest record.** ~180 K БИН have more than one record (almost always exactly two): an old ingest (address in CAPS, previous name) and the current one (modern address, current name, `_id == id`, `datereg` carrying a timezone — `2016-03-29+06:00`). `record_rank()` picks the newest by **registration date first, current ingest as tie-break**. Only the newest record's status matters: anything other than «Зарегистрирован» goes into the flagged list (9 БИН at the time of writing — liquidated entities are normally *deleted* from gbd_ul rather than marked). `ResidentCheck.registryStatus(bin)` → `0` ok · `1` ликвидирован · `2` реорганизован · `3` прочее. **Presence still decides residency** — a liquidated company is still резидент — but the UI shows it amber («резидент · ликвидирован», batch cell `✓ ликв.`).

**egov after the redesign (P30.11 → fgw.egov.kz / P3011).** egov.kz was rebuilt as a Next.js app and the old JSF endpoint `https://egov.kz/services/P30.11/rest/gbdul/organizations/{bin}` (cookie session) is gone. The portal is now only a front end; data goes through the gateway **`https://fgw.egov.kz`** with a **Bearer token**, and the service is coded **`P3011`** (no dot). Our lookup is `GET /v1/P3011/organizations?bin={12 digits}` → `{code:'SUCCESS', data:{organization_info_list:[{bin,name_ru,name_kz}]}}`; the same path exists for P3001/P3002/P3005/P3006 (one shared ГБД ЮЛ search). Error codes arrive in `code` (even on HTTP 200): `ORGANIZATION_NOT_FOUND_BY_BIN`, `ORGANIZATION_LIQUIDATED`. **The `resident` boolean is gone** — residency is now derived from the fact itself: found in the Min-Justice register of legal entities → резидент, not found → нерезидент (exactly what the old boolean encoded), and **`ORGANIZATION_LIQUIDATED` → резидент + «ликвидирован»** (the old API returned `resident:false` for status 034, i.e. a false нерезидент; the app already treats a liquidated company as резидент-with-a-flag in the local index, and `_egovVerdict` now returns `registryStatus:1` for it — the batch cell shows `✓ ликв.`). `registrationDate`/`incorporationCountry` are no longer returned (stat.gov.kz / kyc.kz cover them). **The token is not a cookie**: it lives in `localStorage['identity_data'] → state.identityData.auth.{access_token, refresh_token}` (zustand persist), so `getEgovToken()` in the extension reads it with `chrome.scripting` from an open `egov.kz/*` tab, or opens a background tab, reads and closes it. **Tokens are short — access 10 min, refresh 20 min — and the refresh token is SINGLE-USE** (measured live). Token lifecycle (extension 0.7.0, built after the user reported constant egov logouts and flashing tabs): the pair is cached in `chrome.storage.session` (`egovAuthPair`) and refreshed by **plain fetch** (`POST https://fgw.egov.kz/identity/v3/auth/token/refresh`, Bearer access, body `{refresh_token}`); **background egov tabs are never opened** (the old open-read-close flow visibly flashed tabs at the user). After every refresh the new pair is written into **all** open egov.kz tabs' localStorage **plus a synthetic StorageEvent** — the portal keeps its pair in memory (zustand) and doesn't see a bare localStorage write; without the event it re-sent the burnt refresh token and got logged out. A `document_start` content script **`egov-sync.js`** seeds localStorage with the cached pair when egov.kz opens (only if newer by access-token exp) so the portal never boots with a burnt refresh token. **Keepalive is passive** (`getEgovToken({passive:true})` — look, don't refresh): burning the single-use token on a 5-minute timer was the root cause of the logouts. Token fetches are single-flighted (`egovTokenInFlight`); a 401 drops the cached access and retries once. Note the error convention: **«not found» comes back as HTTP 412** with a normal JSON body, so `resp.ok` is not checked — the verdict comes from `code`. `fetchEgovResidencyLegacy` keeps the old endpoint as a fallback when no token exists. `host_permissions` needed `https://fgw.egov.kz/*` (extension 0.6.0 — **reload the unpacked extension** after pulling). Login lives at `https://egov.kz/ru/identity/main` (QR via eGov Mobile or ЭЦП); other endpoints seen in the bundle, if ever needed: `/identity/v3/auth/{qr,eds,verify,otp/send,user/info}`, `/identity/v3/auth/token/refresh`, and per-service `/v1/{CODE}/{xml,signing/send-eds,request-status}`.

**egov = the authoritative override (via the extension bridge).** The open-data gbd_ul **lags** — recent registrations (e.g. all 2025 БИНs tested) are absent from it *and* from its live API, so "absent → нерезидент" produces **false нерезидентов**. The real residency source is the tax register behind egov service e_084: `GET https://egov.kz/services/P30.11/rest/gbdul/organizations/{bin}` returns `{resident: true|false, status.code, shortName, registrationDate, incorporationCountry}` — an **authoritative `resident` boolean**. It needs the user's egov portal session, so the Chrome extension fetches it (`EGOV_RESIDENCY_LOOKUP`, `credentials:'include'`) exactly like it bridges stat.gov.kz. Architecture is **hybrid**: the local index gives an **instant** verdict (offline, no network); when the bridge is available, `ResidentCheck.checkEgov(bin)` fetches the **authoritative** answer and overrides — so only the checked БИН hits the network, not "every БИН like qazyna". **Request budget (P3011 is a named gov-service request, visible in the user's egov history — send the absolute minimum):** the lookup runs against **P3001** first with **P3011** as fallback (`EGOV_FGW_SERVICES`) — verified live that both return identical org-search payloads, so the verdict is unchanged; note «not found» arrives as **404 on P3001 but 412 on P3011**, which is why the verdict reads the `code` field and never `resp.ok`. All egov traffic funnels through `ResidentCheck.fetchEgovRaw(bin)` — the ONLY network entry point, shared by `checkEgov`, the batch pool and the dossier; raw responses cache in `_egovRaw` + definite ones persist 12h in `localStorage['egov_resid_v1']` (`EGOV_TTL_MS`, lazy `_egovStoreInit`, debounced writes) so page reloads / re-runs of the same реестр make zero requests; ANY failure (dead session, 5xx, timeout) sets a global `_egovPauseUntil` pause (`EGOV_PAUSE_MS` = 5 min) — previously failures were deliberately not cached, so every preview repaint retried and the app hit egov «без конца», scaring the user. The extension mirrors this with `egovNoSessionUntil` (60s, v0.7.1): no token + legacy path failed → no new network attempts for a minute. egov verdict (`_egovVerdict`) is driven **only by the authoritative `resident` boolean**: `resident:true` (status 002) → резидент; **`resident:false` (any status — 033/034/031/…) → нерезидент**. The status text goes in the tooltip as the reason. **Do NOT map `033` to ИП** — its full text is «является ИПс, а сведения предоставляются только по субъектам, зарегистрированным Минюстом РК», i.e. "this БИН is not a Min-Justice-registered KZ legal entity, no data" → нерезидент (this was a real bug: type-6 БИНs the user classifies as нерезидент were shown as ИП). **ИИН guard:** the endpoint is БИН-only — an ИИН returns `031`/`resident:false` which would be a false «нерезидент», so `checkEgov` **skips ИИН** (`idKind !== 'bin'`) and keeps the **local** `individual` verdict «ИП (ХЗ)». So «ИП» comes **only** from the local ИИН path (5th digit 0–3), never from egov; egov БИНs (5th digit 4/5/6) are strictly резидент/нерезидент. Badge/card show the source: `· egov` vs `· ГБД ЮЛ от DD.MM.YYYY`. Degrades gracefully: no extension / not logged into egov → stays on the local index verdict. Wired into **both** surfaces: (1) the single-БИН check (Проверка контрагента / Андеррайтинговое решение) via `App._applyResidency` (async egov override, loop-safe through the sync `egovResolved` cache); (2) the batch «Проверка Договоров» via `BatchAR._poolEgovResidency` (a background pool started from `startStatgov` alongside `_poolEgov`, `EGOV_RESID_CONCURRENCY=6`) — the local index fills each cell instantly, egov refreshes the affected rows as answers land. Both read the shared `ResidentCheck.egovResolved` cache: `BatchAR._residVerdict(bin)` = `egovResolved(bin) || check(bin)` feeds `_residBadge`, `_residStatusRank` (the «Нерезиденты» filter), and `_resultCounts` (HTML report), so egov overrides everywhere consistently. **Pending state:** while egov hasn't answered, a БИН cell shows **⏳** (not the preliminary local verdict) — gated by `BatchAR._egovResidPhase` (`'pending'` set on load / in `startStatgov`; `'unavailable'` if no bridge → fall back to local; `'done'` when `_poolEgovResidency` finishes → unresolved БИН fall back to local). ИИН skip ⏳ (never sent to egov → immediate local «ИП»). Similarly the «Дата рег.» column shows **⏳** until the **kyc fallback finishes** (`BatchAR._kycFinished`) so `_regCell` doesn't flash the intermediate БИН-derived date / «найдено без даты» before kyc has had its turn. **Class-column highlighting:** the «Класс (К)» cell shows only the per-ОКЭД class list — **never the tariff** (it's a class column); and the class list text is neutral — the **cell** carries the err/warn colour (`batch-cell--err/warn`), not a second colour on the value, to avoid double-highlighting.

Statuses — `resident` / `nonresident` / `individual` / `invalid` / `unavailable`:

- **ИИН ≠ БИН.** ГБД ЮЛ holds legal entities only, so the «absent → нерезидент» rule must NOT be applied to ИИН — in a real contracts export ~38% of rows are ИП and would all turn нерезидент. БИН and ИИН are told apart by the **5th digit**: `4|5|6` → БИН (4 — резидент, 5 — нерезидент, 6 — совместная деятельность), anything else → ИИН (there the 5th digit is the tens of the birth day, 0–3). ИИН gets `status: 'individual'`, label **«ИП (ХЗ)»**, and **`nonResident: null`** — residency of an ИП is **not determined automatically** (neither the ЮЛ registry nor egov P30.11 checks it, and some ИП are non-residents), so the checkbox is **not** auto-set and the underwriter decides. The egov 033 («является ИП») verdict is the same «ИП (ХЗ)» / `nonResident: null`.
- If the index file is missing / fails to load, status is `unavailable` and **nothing is auto-filled** (the checkbox is left to the underwriter) — never silently marks everyone нерезидент.

Where it plugs in:

- **Проверка контрагента / Андеррайтинговое решение** — `App._applyResidency()` (single computation point, called from `_refreshDerivedData` and `showPreview`) sets `App.residency` **from the Страхователь БИН (`zayavka.bin`)**, ticks `#nonResident` and renders the `#resident-status` badge. In the profile card, Страхователь and Контрагент are **separate rows** (different БИН = different data): `App._residencyHtml()` = Страхователь (honours the manual checkbox override), and when a registry-loaded case has a distinct контрагент (`App._hasDistinctContragent()`) a second row «Признак резидентства (контрагент)» = `App._residencyContrHtml()` (Контрагент = `zayavka.binContragent`, always auto). Single-БИН checks (Проверка контрагента tab, manual input) have no separate контрагент → one unlabelled row. The checkbox and `data.nonResident` in single-case documents always track the **Страхователь**. Badge helper: `App._residBadgeHtml(res)`.
- **Manual override wins.** Toggling the checkbox fires `App.onNonResidentToggle()` → `App._residencyManual = true`, and auto-fill stops overwriting it until a new case is loaded (`_resetFormState` clears the flag). The badge then reads «резидент · вручную (по ГБД ЮЛ — нерезидент)».
- **Проверка Договоров** — ONE «Резидент» column, for the **Страхователь only** (the Контрагент column was removed — the export carries residency for the insurer only). It follows the table-wide convention: **top line, black = value from the выгрузка**; **bottom line, grey in parentheses = value from the egov registry**. Top (`_residRegistryStatus`, from `residencyCountry`): `✓` Казахстан · `нерез.` any other country · `отсутствует` when the column is blank (nothing to compare — egov below is taken as the correct value). Bottom (`_residEgov`): `(✓)` · `(нерез.)` · `(ИП)` (ИИН — residency of an ИП is not computable, never a mismatch) · `(отключен)` when there is **no egov connection** — the check is then not performed at all, no local-index fallback is shown · `(⏳)` while checking · `(н/д)` if egov didn't answer for that БИН. **The batch table never falls back to the local ГБД ЮЛ index** (it lags → false нерезиденты); the local index still backs the single-БИН check. `_residRegDiff` flags a mismatch only when **both** sides are definite (registry resident/nonresident AND egov resident/nonresident) — it paints the cell **and the row** red, and `_rowState` returns `'err'` for it **even before statgov finishes**, since the comparison doesn't depend on statgov (otherwise the grey «в очереди» state would mask it). `_residEffStatus` (egov if answered, else the выгрузка) feeds the «Нерезиденты» filter and the `_resultCounts` counters (`nrS`/`ipS`/`residDiff`/`egovOff`).
- **«⬇ Скачать результаты проверки (HTML)»** (`#batch-download-html` → `BatchAR.downloadResults`) — exports the whole reviewed registry as **one self-contained HTML report** (opens in any browser, prints to PDF). Visible whenever rows exist; **not gated on stat.gov.kz**. Key detail: the live table holds only the chunks scrolled to, so `downloadResults` builds **all** rows with `_rowsHtml(_displayOrder())`, splices them into a copy of the table's `outerHTML` and parses that into a detached `<div>` — the live table is never re-rendered (that is what used to hang on big registries). The snapshot is cleaned (approve checkbox → static ✓/—, all `onclick`/`oninput` stripped, inputs disabled), then `_buildResultsHtml` wraps it: header (timestamp, source filename `_sourceFileName`, ГБД ЮЛ base date, active sort), a summary chip row (`_resultCounts`: ok/warn/err/approved/unchecked + a purple «свыше лимитов АС (договоров: K)» chip mirroring the on-screen status bar, shown only when non-zero), a colour legend (incl. the purple-outline key and the residency badge key), and the full table. **No «Резидентство сторон» chip row and no residency explainer in the footer** — both were removed at the user's request (the признак is already visible in the «Рези-дент (С)/(К)» columns); `_resultCounts` still computes `nrS/nrK/ipS/ipK` for the on-screen UI. The footer is just «Отчёт сформирован приложением Underwriting Suite (Standard Life).» `style.css` is **inlined** (fetched at export time) for standalone fidelity + a print block (`@page A4 landscape`). Downloaded via `saveAs` (FileSaver) as `Результаты проверки договоров DD.MM.YYYY (N).html`.
- **Documents** — `data.nonResident` (from the checkbox = Страхователь) drives «Признак резидентства – резидент/нерезидент» in `ar-generator.js` / `zakl-generator.js`; filled automatically. The batch АР/ДАиП form appends the verdict to the existing «БИН/ИИН» row (`ARForm._residencySuffix(row.bin)` → `123456789012 — резидент`) instead of adding a row — the form is tuned to exactly one A4 page. That row prints `row.bin` (the Контрагент/филиал the document is about), so the suffix is **that entity's** residency — it matches the «К» line of the batch table (or the single line when Страхователь = Контрагент). The Страхователь БИН is not printed in the batch document, so it carries no separate suffix; both parties are reviewed in the Проверка Договоров table before generation. `_collectData()` also exposes `residencyStatus` / `residencySource` / `residencyNote`, and the analytics snapshot carries `zayavka.residency` (`App._residencySnap()`), used by the «Признак резидентства» tile on the dashboard.

## Payment installment schedule

**Real tranches from the выгрузка take priority.** The contracts export has `ПорядокОплаты` + repeating `Этап{N}Дата` / `Этап{N}Сумма` columns (N = 1…12; **column positions vary between export versions → matched by header**, not letter). `BatchReader._resolveEtapCols()` + `_rowTranches()` walk the stages until a stage is **fully empty** (no date AND no sum) and attach `row.tranches = [{date, amount}, …]` (so 4 filled stages ⇒ 4 tranches, not 5). The **«Проверка договоров»** table has a **«Транш оплаты»** column (`_trancheCell`/`_trancheCount`): «—» for «Единовременно», else the tranche count (number of filled Этап sums); the toolbar chip «⏳ Транши» **filters** the table down to contracts with installments (see the filter chips below). `applyRegistryRow` copies them onto the case as `zayavka.tranchesFromFile` (dates as ISO strings, persistence-safe). `zayavka.tranchesFromFile` is also the **single source of truth for the editable tranche list** in Шаг 1: selecting «В рассрочку» shows `#manual-tranches` (one editable date+amount row per tranche; **count = number of rows**). `onPaymentChange` auto-seeds it by the current frequency when empty (via `fillTranchesByFreq` → `calcPaymentTranches`, amounts blank), the «↻ По периодичности» button / `#paymentFrequency` change regenerates it, and `addManualTranche`/`removeManualTranche`/`updateManualTranche` edit it (dates kept as ISO via `_dateInputToIso`/`_isoToDateInput`, amounts via `_parseMoney`). `_collectData` builds the schedule text from whatever rows are in `tranchesFromFile`. So registry-loaded tranches are pre-filled and editable; manual/заявка cases start from the frequency cycle and can be hand-tuned to an arbitrary count. The editor requires `App.zayavka` (it stores onto it); a missing case shows a hint.

When user picks «В рассрочку» + frequency (and there are no real file tranches), `Utils.calcPaymentTranches()` generates a **fixed annual cycle** (not based on contract duration):

| Frequency | Tranches per year |
|---|---:|
| year / halfYear / quarter / month / week / day | 1 / 2 / 4 / 12 / 52 / 365 |

First tranche is always `today + 1 day`. Long lists (>14) are auto-formatted to `«1 транш — DD.MM.YYYY; 2 транш — ... ; N транш — DD.MM.YYYY (всего N траншей, раз в неделю)»`.

## Document margins and tab stops

All docx generators use **A4 with symmetric 2 cm margins** (1134 twips). The available content width is `9638 twips`. Long lines that must span full width (e.g. director signature with name aligned to the right edge) use right-aligned tab stops at `9638`, not literal space characters.

AR uses a 3-column invisible-border table for the signature block so name/line/date columns align vertically across all members — see `ar-generator.js` `sigRow()` helper. Don't replace this with manually-spaced paragraphs.

## statsnet is manual-only

`App.autoLookupStatsnet` is **never called automatically** — not from `quickLookupByBin`, not from заявка load, not from `applyManualZayavka`, not from `applyRegistryRow` (all four auto-runs were removed). Reason: it searches via Яндекс and opens background tabs, taking 30–60 s — with it inside `Promise.allSettled` the whole «Проверка контрагента» looked stuck, while the actual stat.gov lookup answers in 1–2 s (same call the batch check uses). The only entry point is the explicit «🔎 Найти отрасль через statsnet» button; each new-БИН flow resets `App.statsnet = null` so the diagnostics line shows «ещё не запускался» instead of the previous company's industry.

## AI consultant ("Спросить ИИ")

Split into two shared modules used by **both pages**:

- `js/ai-prompt.js` — `AIPrompt.build(snap)` builds the ~9K-char prompt from an analytics *snapshot* only (no DOM/App access).
- `js/ai-consultant.js` — `createAIConsultant(getPrompt, opts)` drives the right-side slide-over panel (same element ids on both pages: `ai-panel`, `ai-overlay`, `ai-prompt-text`, …).

On `analytics.html` (standalone tab) the floating FAB works as before. In **inline mode** (`body.is-inline`, iframe on index.html) the in-iframe FAB/panel are hidden entirely — `position: fixed` inside the auto-height iframe would land at the very bottom of the content. Instead `index.html` provides its own "Спросить ИИ" button in the analytics CTA row plus a parent-page FAB (visible while `body.inline-analytics-open`), both opening `App.AI` — a `createAIConsultant` instance that builds the prompt on the fly from `App._buildAnalyticsSnapshot()`.

The prompt deliberately:
- Excludes identifying data (no insurer name, no BIN, no address)
- Asks the AI to recompute key actuarial metrics independently (don't pre-compute and present)
- References KZ legislation (Закон РК № 30-III от 07.02.2005, Соц. кодекс ст. 195-1, АРРФР, Solvency II)
- Avoids biasing the AI with the current underwriter's verdict

`AIConsultant.sendTo(service)` copies the prompt to clipboard, opens the AI service in a new tab. For ChatGPT/Perplexity, also tries URL prefill via `?q=...` (only if encoded prompt fits in ~1900 chars — usually not, since our prompt is ~9K). Full auto-submit is impossible due to same-origin policy.

## Досье по БИН/ИИН (`js/dossier.js`)

One page that shows **everything the app knows about a single БИН/ИИН**, from every source it can reach. Two surfaces, one builder — `Dossier._sections(ctx)` produces the section model and `Dossier._html(ctx)` renders it, so both surfaces always show the same thing:

- **«Проверка Договоров»** — the БИН of Страхователь and of Контрагент in the table are clickable (`BatchAR._idLink` → `.batch-id-link` → `Dossier.openFromRow(idx, 'insurer'|'contr')`) and open the dossier **in a new tab**. `window.open` is called **synchronously in the click handler** (an `await` first would get it blocked as a popup — see gotchas); the tab gets a shell that `<link>`s the app's `css/style.css`, so the `.ds-*` rules are shared with the inline copy. The clickable id is a `<span role="button">`, not `<button>`/`<a>`, so the HTML report (`downloadResults`, which strips `onclick` and disables controls) keeps it as plain text instead of a dead control.
- **«Проверка контрагента» + «Андеррайтинговое решение»** — the same dossier inline, as THE profile of both tabs (`#dossier-contractor` and `#dossier-decision`, both listed in `Dossier._SINGLE_MOUNTS` and painted by `Dossier.renderSingle()` at the end of `showPreview` from one shared ctx). It repaints **only its own containers** — going back through `showPreview` would loop, because enrichment repaints. A mount rendered inside a hidden tab (`display:none`) measures zero card heights, so `App.switchTab` calls `Dossier.relayoutMounts()` (rAF) to redo the masonry spans for the mount that just became visible (`offsetParent !== null` guard skips still-hidden ones).

**Organised by DATA, not by source.** A row is a *field* («Наименование», «Руководитель», «КАТО»); inside it every known value is listed with its source in grey (`.ds-src`). Values that match collapse into one line listing all of them («stat.gov.kz · kyc.kz»); values that differ stay side by side and get an amber «источники расходятся» marker (`Dossier._vals` / `_row` do the grouping; comparison keys are normalised per field type — `_nameKey` drops ТОО/«»/case, `_addrKey` drops punctuation, dates are formatted first so kyc's ISO `2012-04-11T00:00:00Z` collapses with stat.gov's `11.04.2012`). This is the point of the page: the underwriter sees one card, and disagreements between registries pop out instead of being buried in three near-identical blocks. Source captions live in `Dossier.SRC` — one place, reused by every row and by «Источники».

**Heights are dynamic (JS masonry).** A plain grid stretches every row to its tallest card and leaves holes under the short ones — half a screen of white. CSS masonry is Firefox-only, so `Dossier._layout(root, win)` does the classic trick: measure natural heights in normal grid mode, then switch the grid to `.ds-grid--masonry` (`grid-auto-rows: 4px`, `row-gap: 0`, `grid-auto-flow: row dense`) and set each card's `grid-row-end: span ceil((h + 16) / 4)`. It runs after every paint (both hosts), on resize, and on `toggle` (captured — `toggle` doesn't bubble) because expanding «N версий» / a raw table changes the height. **Measure first, switch mode second** — in masonry mode an unspanned card collapses to 4 px, so measuring after the switch gives garbage. If the script never runs, the plain grid remains (degrades, doesn't break).

**Every source also gets a full «все поля» card** (`_secSourceCards`, `span: 'full'`): stat.gov.kz renders its `_raw` label→value pairs verbatim (that is where ЛИН, «Местонахождение ИП», «Код/Наименование КРП», КАТО, «Код/Наименование сектора экономики» live — the mapped fields above are a subset), kyc.kz shows the mapped card plus its raw payload, egov P3011 its whole JSON, e-Qazyna the search result (found, **share %**, name, status) plus the «Дополнительные сведения» block. The rule the user set: the dossier must contain **everything** a source returned, not only what we decompose into cards.

## Common gotchas

- **`activityType` dropdown is gone** — it was removed when ОКЭД input took over. If you see code reading `document.getElementById('activityType').value`, that's a bug (it returns null). Use `App._resolveOked()` instead.
- **`data.docDate` is the date from F3 of заявка** (date of application submission), not `periodFrom`. Don't override with contract dates.
- **Affiliated lookup is by raw БИН string** (12 digits). Always strip whitespace before comparing.
- **`window.open` from inside a click handler** is required for "Open in new tab" — calling it from an async chain after `await` will be blocked by browser as a popup.
- **Signer defaults live in TWO places — keep them in sync**: `App.SIGNERS_DEFAULTS` + `App.SIGNERS_ROLES` (js/app.js, the editable form source of truth, rebuilt into `Utils.*` at runtime + the `#sgn-*` inputs in index.html — adding a member means adding a `sgn-row-*` block AND the `buildMembers([...])` key) and the hardcoded fallbacks in `js/utils.js` (`AS_MEMBERS`, `PRAVLENIE_MEMBERS`, `UPRAV_DIR_ROLE/NAME`, …). Order = array order. **Both `pravlenie` and `sd` organs use `PRAVLENIE_MEMBERS`** (АР `ar-generator.js` + Протокол `protocol-generator.js`), and the АР member header is **«Члены Правления» for both** (`membersHeader`); `as` uses `AS_MEMBERS` / «Члены Андеррайтингового Совета». Current defaults: Правление (4) = Амерходжаев (Председатель) · Кныкова · Аринов · Ашимов (last three all «Заместитель Председателя Правления, член Правления»); АС (6) has Аринов at position 3; Директор ДАиП = **Бурханов Д.К.** (also `ar-form.js` `UNDERWRITER` for batch АР + заключение signer); СЗ-СД recipient `sdChair` = «М.К. Альжанову» (dative). СЗ subjects/details depend on `data.organ`: `sz-generator.js` — Правление-limit → «…рассмотрение Правления…»; **SD-limit sz_pravlenie → «…рассмотрение Совета директоров…решении о заключении {крупной сделки | сделки с аффил.} (договора ОСРНС)»** and drops the «Страховая премия с учётом ПК»/«Решение по риску» lines; sz_sd → «О заключении крупной сделки[ с аффилированным лицом] (договор ОСРНС)», replaces «Решение по риску» with «Лимит СД – …», drops «со стандартным коэффициентом».
- **Dates with the month spelled out use the GENITIVE case** («02 июля 2026», not «02 июль»): `Utils.RUSSIAN_MONTHS_GEN` (via `fmtDateRu`), `ar-form.js` `MONTHS_GEN`, `protocol-generator.js` `MONTHS_GEN`. Never format a date with the nominative `RUSSIAN_MONTHS` / `MONTHS_NOM`.
