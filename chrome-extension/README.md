# Standard Life — мост к stat.gov.kz

Мини-расширение для Chrome, которое позволяет нашему андеррайтинговому приложению
тянуть данные с `stat.gov.kz` по БИН, используя текущую ЭЦП-сессию пользователя.

## Зачем

`stat.gov.kz` не отдаёт CORS-заголовков, и сессия после ЭЦП живёт только в браузере
пользователя. Cloudflare Worker (как для `pk.uchet.kz`) тут не сработает — у него нет
твоего ЭЦП. Расширение получает `host_permissions` к обоим доменам и работает как мост.

## Установка (dev)

1. Открой `chrome://extensions`
2. Включи **Developer mode** в правом верхнем углу
3. Нажми **Load unpacked**
4. Укажи папку `underwriting-app/chrome-extension/`
5. Перезагрузи вкладку нашего приложения (`localhost:8085` или GitHub Pages)

## Как проверить, что мост работает

В консоли приложения:

```js
await StatGovClient.ping()
// → { ok: true, version: '0.1.0' }
```

Если `ok: false` — расширение не загружено или origin не в `host_permissions`/`content_scripts`.

## Использование

```js
const data = await StatGovClient.lookup('130740005369');
// data → { bin, name, okedPrimaryCode, ... }
```

## Источники данных (lookups)

Расширение проксирует несколько источников по БИН/ИИН (12 цифр). Каждый — отдельный
тип сообщения `{source:'sl-app', type, requestId, bin}` → ответ
`{source:'sl-bridge', type:'<TYPE>_RESULT', requestId, ok, data, error}`.

| Тип | Источник | Авторизация | Что отдаёт |
|---|---|---|---|
| `STATGOV_LOOKUP` | stat.gov.kz (кабинет) | нужна ЭЦП-сессия | официальная карточка, ОКЭД, КРП, адрес, дата рег. |
| `STATSNET_LOOKUP` | statsnet.co (через поиск) | не нужна | «Отрасль», основной ОКЭД (медленно, открывает вкладки) |
| `KYC_LOOKUP` | kyc.kz | **не нужна** | базовая карточка из SSR-страницы (быстро, обычный GET) |
| `EGOV_HEALTH` | — (локально) | — | статус сессии egov для индикатора: `{token, hasPair, tabOpen, paused}`. **Строго пассивно**: читает кэш пары/localStorage вкладок, в сеть НЕ ходит и одноразовый refresh НЕ тратит. `tabOpen` нужен, чтобы отличить «сессии нет» от «состояние не видно» (нет ни кэша, ни вкладки egov.kz — тогда приложение показывает нейтральное «сессия не видна», а не красное «нужен вход»). |
| `EGOV_RESIDENCY_LOOKUP` | fgw.egov.kz (услуга P3001, запасная P3011) | **нужен вход на egov.kz** | резидентство: `GET https://fgw.egov.kz/v1/P3001/organizations?bin={bin}` с `Authorization: Bearer <token>` → `{code, data.organization_info_list:[{bin,name_ru,name_kz}]}`. Найдена → резидент; `ORGANIZATION_NOT_FOUND_BY_BIN` → нерезидент; `ORGANIZATION_LIQUIDATED` → резидент + пометка «ликвидирован». Код HTTP при «не найдено» зависит от услуги (P3001 → 404, P3011 → 412), поэтому вердикт определяется полем `code`, а не статусом. |

### egov: новый портал (редизайн)

egov.kz переехал на Next.js, старый JSF-эндпоинт `/services/P30.11/rest/gbdul/organizations/{bin}`
(куки-сессия) снят. Теперь фронт ходит в шлюз **`https://fgw.egov.kz`** с **Bearer-токеном**;
услуга «о госрегистрации юрлица и его подразделений» доступна и как **P3001** («Справки/сведения по
юридическим лицам» → тип «О госрегистрации юрлица и его подразделений»), и как **P3011**; поиск
организации по БИН — `GET /v1/{услуга}/organizations?bin=…` (тот же путь у P3002/P3005/P3006 —
это общий поиск группы услуг ГБД ЮЛ). **Основная услуга теперь P3001**, P3011 — запасная
(`EGOV_FGW_SERVICES`): проверено под живой сессией, на шаге поиска организации обе отдают
одинаковый ответ, поэтому вердикт резидентства от смены услуги не меняется.

Токен лежит **не в куках**, а в localStorage портала:
`localStorage['identity_data'] → state.identityData.auth.{access_token, refresh_token}` (zustand-persist).
Поэтому `credentials:'include'` больше не работает: `getEgovToken()` читает пару через
`chrome.scripting` из уже открытой вкладки `egov.kz/*` либо берёт её из кэша
`chrome.storage.session` (см. ниже) — фоновые вкладки не открываются.

**Токены короткие: access — 10 минут, refresh — 20** (замерено на живом портале). Одной
пакетной проверки реестра хватает, чтобы протухнуть несколько раз, поэтому мост обновляет
токен сам — тем же вызовом, что и портал:

```
POST https://fgw.egov.kz/identity/v3/auth/token/refresh
Authorization: Bearer <access_token>;  body {"refresh_token": "..."}
→ 200 { code:'SUCCESS', data:{ access_token, refresh_token } }
```

Refresh-токен **одноразовый**, поэтому жизненный цикл пары построен так (v0.7.0):

- пара кэшируется в `chrome.storage.session` **и в `chrome.storage.local`** (`egovAuthPair`): session
  чистится при перезагрузке расширения и рестарте браузера, после чего сессию было видно только
  при открытой вкладке портала — индикатор писал «нужен вход» залогиненному пользователю.
  `egovPairUsable()` выбрасывает пару, у которой протухли ОБА токена, поэтому мёртвая пара
  не может изобразить живую сессию; обновляется пара **чистым fetch** —
  **фоновые вкладки egov.kz не открываются вообще** (раньше мигали у пользователя);
- после нашего refresh новая пара пишется в localStorage **всех** открытых вкладок портала
  плюс кидается synthetic `StorageEvent` — портал держит пару в памяти (zustand) и одну лишь
  запись в localStorage не видит; без события он слал старый сгоревший refresh и разлогинивался;
- **`egov-sync.js`** — content-script на egov.kz (`document_start`): при открытии портала
  спрашивает у background кэшированную пару и, если она новее лежащей в localStorage
  (по exp access-токена), подменяет её ДО старта приложения портала — иначе портал стартует
  со сгоревшим refresh и мгновенно вылетает;
- **keepalive пассивный**: только проверяет живость access (`getEgovToken({passive:true})`),
  refresh по таймеру ЗАПРЕЩЁН — трата одноразового токена раз в 5 минут и была главной
  причиной «постоянно вылетает из egov»;
- single-flight (`egovTokenInFlight`): пул из 6 воркеров не устраивает 6 параллельных refresh;
  на 401 access сбрасывается и запрос повторяется один раз;
- если пары нет ни в кэше, ни во вкладке — `fetchEgovResidency` откатывается на старый
  эндпоинт (`fetchEgovResidencyLegacy`); пользователю достаточно один раз открыть egov.kz
  и войти — дальше мост живёт на кэше;
- **отсечка «сессии нет»** (`egovNoSessionUntil`, v0.7.1): когда токена нет и legacy-путь
  тоже упал (или refresh исчерпан), минуту новые сетевые попытки не делаются — иначе
  пакетная проверка на мёртвой сессии молотила egov.kz десятками бессмысленных запросов.

**Бюджет запросов на стороне приложения** (`js/resident-check.js`): P3001 — именной запрос
госуслуги под аккаунтом пользователя (виден в истории egov), поэтому приложение шлёт минимум:
`ResidentCheck.fetchEgovRaw` — единственная точка запроса (checkEgov, досье и пакетный пул
делят кэш сырых ответов), определённые ответы живут 12 ч в `localStorage['egov_resid_v1']`
(перезагрузка страницы / повторный прогон реестра в сеть не ходят), любая ошибка включает
общую паузу 5 минут.

Ответы (проверено вживую): найдена — HTTP 200 `code:'SUCCESS'` + `organization_info_list`;
не найдена — `code:'ORGANIZATION_NOT_FOUND_BY_BIN'` с нормальным JSON-телом, но **код статуса
у услуг разный: P3001 → 404, P3011 → 412**. Поэтому `resp.ok` и статус вообще не смотрим —
вердикт определяет только поле `code`; иначе «нерезидент» превращался бы в ошибку запроса
при каждой смене услуги.

Что потеряли при переезде: признак `resident` отдельным полем и `registrationDate` /
`incorporationCountry` — новый эндпоинт их не отдаёт. Резидентство выводим из самого факта
наличия организации в реестре юр. лиц РК (это и есть смысл старого `resident`), дату регистрации
и так дают stat.gov.kz / kyc.kz.

### kyc.kz (`KYC_LOOKUP`)

`https://kyc.kz/search/company/{БИН}` отдаёт SSR-страницу (~250 КБ) без ЭЦП, cookies,
капчи и Cloudflare. Карточка вшита в `window.__NUXT__=(function(a,b,..){return {...}}(args))`
— это минифицированный IIFE, где часть значений — ссылки на параметры функции,
подставляемые хвостовыми аргументами. В service worker MV3 `eval`/`new Function`
запрещены, поэтому `parseKycNuxt()` разбирает его строками: считывает параметры и
аргументы (карта подстановки), сбалансированными скобками вырезает `data:[{result:{…}}]`,
резолвит литералы и плейсхолдеры.

Контракт — такой же, как у `STATGOV_LOOKUP`/`STATSNET_LOOKUP`: страница шлёт
`postMessage` и слушает ответ. Обёртки `StatGovClient.lookupKyc()` пока нет — её
можно добавить позже по аналогии с `StatGovClient.lookup()`. Быстрая проверка из консоли:

```js
const reqId = 'kyc-' + Math.random().toString(36).slice(2);
window.addEventListener('message', function h(e) {
  if (e.data?.source === 'sl-bridge' && e.data.type === 'KYC_LOOKUP_RESULT' && e.data.requestId === reqId) {
    window.removeEventListener('message', h); console.log(e.data.ok, e.data.data || e.data.error);
  }
});
window.postMessage({ source: 'sl-app', type: 'KYC_LOOKUP', requestId: reqId, bin: '830318351135' }, '*');
// data → { bin, name, isIndividual, okedPrimaryCode (okat), okedPrimaryName (main_activity),
//          okedSecondary, kato, krpCode, krpName, registrationDate, headFullname,
//          legalAddress, status, isActive, payNds, found, _source:'kyc.kz', _raw }
```

Несуществующий БИН → kyc.kz всё равно отдаёт 200, но с пустой карточкой
(`id:0, title:"-"`); парсер это распознаёт и возвращает `{ found:false }`.

**Скоуп:** только базовая карточка из серверного HTML. Риски/благонадёжность/налоги/
госзакупки грузятся клиентом за авторизацией (JWT/тариф) — их в SSR нет, не парсим.

## Keepalive сессий (stat.gov.kz + egov)

Сессии обеих служб вылетают по бездействию (≈15–30 мин). Расширение раз в **5 минут**
(`chrome.alarms`) делает лёгкий авторизованный GET к stat.gov.kz, сдвигая idle-таймаут
сессии — так один утренний вход держится весь день. Для egov «пинговать» больше нечего
(новый портал авторизуется Bearer-токеном, а не кукой): keepalive лишь ПАССИВНО смотрит,
жив ли access-токен (одноразовый refresh не тратится) — наличие свежего токена и есть
признак живой сессии, фоновую вкладку при этом не открываем. Пинги идут **только пока открыта вкладка
приложения** (закрыл на ночь → сессии истекают сами). Требует разрешение `alarms`.
Статус можно запросить сообщением `KEEPALIVE_STATUS` (`{lastRun, statgov, egov, periodMin}`).
Оговорка: продлевает только **idle**-таймаут; если у службы есть жёсткий предел длины сессии —
один перелогин за смену всё равно потребуется.
